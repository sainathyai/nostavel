# Threat model: LiteAPI webhook receiver

- **Author:** security-architect
- **Date:** 2026-09-17
- **Code in scope:**
  - `src/app/api/webhooks/liteapi/route.ts` (entry point)
  - `src/lib/webhook-auth.ts` (shared-secret verification)
  - `src/lib/webhook-format.ts` (envelope parsing, field extraction)
  - `src/lib/booking-service.ts` (`recordSupplierCancellation`)
  - `src/db/schema.ts` (`webhookEvents`, `bookingEvents`, `cancellations`, `bookings`)
- **Status:** current
- **Review:** generated by the security-architect role during the Segment 2.4 live check; corrected in review (see "Review corrections" at the end)

## Summary

The LiteAPI webhook receiver is the inbound path for supplier-initiated booking
lifecycle events (cancellation, refund, amendment, hotel confirmation numbers). It
authenticates via a shared secret in the `authorization` header, stores every delivery
in `webhook_events` before returning 200, and deduplicates on the supplier's `event_id`
using a database unique constraint. The implementation is sound for its current
sandbox-only scope: authentication uses constant-time comparison, idempotency is
enforced at the database level, and dispatch failures do not cause retries. Six gaps
were identified, the most significant being that a refund event cancels the booking
(G6), the non-atomic status-change-plus-event write in `recordSupplierCancellation` (G1),
and the lack of rate limiting on the webhook endpoint (G2).

## Assets

| Asset | Why it matters |
|---|---|
| Booking ledger integrity | A forged or replayed webhook could mark a real booking as cancelled, denying a guest their stay |
| Refund amount accuracy | An attacker-controlled `refund_amount` written to the cancellations table could create a false refund record |
| Webhook shared secret | The sole authentication control; compromise allows arbitrary webhook forgery |
| Guest personal data (contact email, name) | Reachable indirectly through the booking row looked up by `liteapiBookingId`; not returned in the response |
| Append-only audit trail | `bookingEvents` rows are the dispute/reconciliation record; corrupted events undermine trust |

## Trust boundaries and data flow

1. **LiteAPI servers** send an HTTP POST to `/api/webhooks/liteapi` with a JSON body
   and an `authorization` header containing the shared secret.
2. **The route handler** verifies the secret, parses the body, and inserts into
   `webhook_events` (durable storage before ack).
3. **Dispatch** routes `booking.cancel` and `booking.refund` events to
   `recordSupplierCancellation`, which looks up the booking by `liteapiBookingId` and
   writes to `bookings`, `cancellations`, and `bookingEvents`.
4. **The response** is always `{ ok: true }` (or `{ ok: true, duplicate: true }`),
   with no booking data leaked.

The attacker surface is the public HTTP endpoint. The only input the attacker controls
is the HTTP request (headers and body). The `authorization` header is the sole gate.

## Entry points

| Entry point | Method | Authentication | Input | Changes |
|---|---|---|---|---|
| `/api/webhooks/liteapi` | POST | Shared secret in `authorization` header, constant-time comparison (`webhook-auth.ts:13-24`) | JSON body: `event_id`, `event_name`, `request`, `response`, `sandbox` | Inserts `webhook_events`; for cancel/refund events, updates `bookings.status`, inserts `cancellations` and `bookingEvents` |

## Threats and controls

| # | Category | Threat | Control (verified at file:line) | Holds? |
|---|---|---|---|---|
| T1 | Spoofing | Forged webhook from an attacker who does not know the secret | `verifySharedSecret` uses `timingSafeEqual` with length guard (`webhook-auth.ts:11-24`). Returns 401 on failure (`route.ts:30-32`). Secret read from `process.env.LITEAPI_WEBHOOK_SECRET` (`route.ts:30`). | yes |
| T2 | Spoofing | Timing side-channel on secret comparison | `timingSafeEqual` from `node:crypto` (`webhook-auth.ts:11,20`). Length mismatch returns `false` without calling `timingSafeEqual` (`webhook-auth.ts:22`). | yes |
| T3 | Spoofing | Secret is empty or unset in production, allowing any request through | `verifySharedSecret` returns `false` when `expected` is falsy (`webhook-auth.ts:17`). The route would reject every request with 401. | yes (fail-closed) |
| T4 | Tampering | Replayed webhook (duplicate delivery) | `onConflictDoNothing` on `webhookEvents.externalId` unique constraint (`route.ts:53`, `schema.ts:261`). Duplicate returns early without re-dispatching (`route.ts:56-58`). | yes |
| T5 | Tampering | Webhook delivered without an `event_id` bypasses dedup | The handler stores the event without an `externalId` (`route.ts:43-47`). A second delivery of the same no-id event would be stored and dispatched again. However, the no-id path does not dispatch (no call to `dispatch()`), so no double side-effect occurs. | partly -- see G3 |
| T6 | Tampering | Attacker sends a cancel webhook for a booking they do not own | Authentication is the shared secret, not per-booking. An attacker WITH the secret can cancel any booking by `liteapiBookingId`. This is acceptable: the secret is equivalent to supplier trust. Without the secret, 401 blocks. | yes (by design) |
| T7 | Tampering | Crafted `refund_amount` in webhook body writes a false refund to `cancellations` | `extractRefundAmountMinor` converts to minor units (`webhook-format.ts:74-77`). No validation against the booking's `amountTotalMinor`. An authenticated attacker (possessing the secret) could inject any refund amount. | partly -- acceptable given secret = supplier trust, but no sanity bound |
| T8 | Tampering | Non-atomic status change and event write in `recordSupplierCancellation` | Three separate `await` calls: `db.update(bookings)`, `db.insert(cancellations)`, `db.insert(bookingEvents)` (`booking-service.ts:670-687`). A crash between the first and third leaves the booking cancelled without a cancellation row or audit event. Not wrapped in `db.batch`. | no -- see G1 |
| T9 | Repudiation | No log of who delivered the webhook beyond the stored payload | The raw payload is stored in `webhook_events.payload` (`route.ts:52`). The IP, user-agent, and delivery timestamp from LiteAPI are not captured separately. `receivedAt` is `defaultNow()` (`schema.ts:265`). | partly -- payload is stored, IP is not |
| T10 | Information disclosure | Error details leaked in the webhook response | The handler returns `{ error: "unauthorized" }` or `{ error: "bad payload" }` -- generic strings (`route.ts:31,38`). Dispatch errors are caught and logged server-side only (`route.ts:66-70`). No booking data in any response. | yes |
| T11 | Information disclosure | `console.error` in dispatch logs the exception, which could contain supplier data | `console.error("webhook dispatch failed", env.eventName, e)` (`route.ts:70`). If the error contains supplier response data, it lands in server logs. | partly -- acceptable for server logs but worth noting |
| T12 | Denial of service | No rate limiting on the webhook endpoint | No call to `rateLimit` anywhere in the route. An attacker can flood the endpoint with requests, each requiring a database write (even failed-auth requests do not write, but valid-secret requests always insert). | no -- see G2 |
| T13 | Denial of service | Large JSON body exhausts memory | `request.json()` parses the full body (`route.ts:36`). No size limit is set in the route. Whether the framework or hosting platform imposes a limit on route handler bodies was not verified. | unverified |
| T14 | Denial of service | Events without `event_id` accumulate without dedup | Events with no `externalId` are inserted unconditionally (`route.ts:46`). An attacker with the secret could flood with no-id events. | partly -- requires secret, but unbounded |
| T15 | Elevation of privilege | Webhook route does not import `server-only` | The route file (`route.ts`) and `webhook-auth.ts` do not import `server-only`. Next.js API routes are server-only by convention, but the explicit import is the project standard for modules touching secrets. | partly -- see G4 |
| T17 | Tampering | A `booking.refund` event is handled as a cancellation | `dispatch` sends both `booking.cancel` and `booking.refund` to `recordSupplierCancellation` (`route.ts:78-85`), which sets `status: "cancelled"` and writes a `webhook.booking.cancel` event (`booking-service.ts:670-687`). A refund that is not a cancellation (partial or goodwill refund on a stay that still stands) cancels the booking in our ledger. | no -- see G6 |
| T16 | Tampering | Race: concurrent cancel webhook and guest-initiated cancel for the same booking | `recordSupplierCancellation` checks `row.status === "cancelled"` then writes. A concurrent `cancelBooking` could interleave, potentially creating two `cancellations` rows for the same booking. No database-level guard (no unique constraint on `cancellations.bookingId`). | partly -- see G5 |

## Gaps

Filed as tickets on 2026-09-21: G1 → NOS-7, G2 → NOS-13, G3 → NOS-14, G4 → NOS-15,
G5 → NOS-16, G6 → NOS-8. The ticket, not this table, is where the fix is tracked.

| # | Severity | Gap | Failure scenario | Proposed ticket (owner role, acceptance criterion) |
|---|---|---|---|---|
| G6 | Medium | Refund events cancel the booking (`route.ts:78-85`, `booking-service.ts:670-687`) | LiteAPI sends `booking.refund` for a partial refund on a stay that still goes ahead. Our ledger marks the booking cancelled, the guest's trip page shows it cancelled, and the audit event is recorded as a cancel. The guest may abandon a valid stay, and reconciliation against payouts is wrong. | backend-engineer: dispatch `booking.refund` to its own handler that records the refund and an event, and changes status only if the supplier status says cancelled. Label: `money`. |
| G1 | Medium | `recordSupplierCancellation` writes are not atomic (`booking-service.ts:670-687`) | A process crash after `db.update(bookings).set({ status: "cancelled" })` but before `db.insert(cancellations)` leaves the booking marked cancelled with no cancellation record and no audit event. The nightly reconciler would need to detect and repair this, but it has no cancellation row to work from. | backend-engineer: wrap the three writes in `db.batch()` so they succeed or fail together. Label: `security`, `money`. |
| G2 | Medium | No rate limiting on the webhook endpoint (`route.ts`) | An attacker who obtains the webhook secret (or during a secret leak window) can flood the endpoint, causing unbounded database inserts into `webhook_events`. Even without the secret, the constant-time comparison on every request consumes CPU. In the current sandbox-only deployment the practical risk is low. | backend-engineer: add rate limiting keyed on client IP, with a generous limit for legitimate LiteAPI retries (e.g. 60/min). Label: `security`. |
| G3 | Low | Events without `event_id` are not dispatched but are stored without dedup (`route.ts:43-47`) | If LiteAPI ever sends a cancel/refund event without an `event_id` (contrary to their documented envelope), it would be stored but not processed, leaving a supplier cancellation invisible. The no-dispatch path is safe from double-processing but loses the event. | backend-engineer: log a warning when `event_id` is missing so ops can detect it. Label: `security`. |
| G4 | Low | `webhook-auth.ts` does not import `server-only` (`webhook-auth.ts:1`) | The module uses `node:crypto` and handles secret comparison. It is server-only by nature (it uses Node APIs), but the project convention is to mark secret-handling modules explicitly. A bundler misconfiguration could theoretically include it in a client bundle, though `node:crypto` would fail at runtime. | backend-engineer: add `import "server-only"` to `webhook-auth.ts`. Label: `security`. |
| G5 | Low | No unique constraint on `cancellations.bookingId` allows duplicate cancellation rows (`schema.ts:219-233`, `booking-service.ts:670-687`) | A concurrent guest-cancel and webhook-cancel for the same booking could both pass the `status === "cancelled"` check and each insert a `cancellations` row. The booking ends up with two cancellation records, potentially with different refund amounts, complicating reconciliation. In practice the race window is small and the sandbox has low concurrency. | backend-engineer: add a unique index on `cancellations.bookingId` or use `onConflictDoNothing`. Label: `security`, `money`. |

## Out of scope

- **Guest-initiated cancellation flow** (`cancelBooking` in `booking-service.ts`): covered by its own entry point, not triggered by the webhook.
- **Other webhook event types** (`booking.book`, `booking.amendment`, etc.): stored but not dispatched; no side effects beyond the `webhook_events` insert.
- **LiteAPI's own infrastructure** (their retry logic, secret rotation, IP allowlisting): out of scope per `SECURITY.md`.
- **The nightly reconciliation job** (`src/app/api/cron/reconcile/route.ts`): it exists and is the stated safety net for failed dispatches (`route.ts:66-69`); whether it repairs the partial writes in G1 was not verified here.
- **The known gaps in the security rule** (ownership checks on save-guest/confirm, in-memory rate limiting, raw supplier errors): documented separately and not introduced or widened by this code.
